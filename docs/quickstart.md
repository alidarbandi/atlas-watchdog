# Quick start

1. Launch `ATLASWatchdog.exe`. Monitoring and automatic alerts initially show Off. The application is a desktop utility; it is not a Windows service.
2. Try the labeled demo before selecting microscope files. From source, run `python -m atlas_watchdog --demo`. Demo writes only dedicated demo files. Automatic alerts are enforced off; deliberate notification tests say TEST. Settings edits stay in memory during demo; **Exit demo** restores the original source configuration with both controls off. Credential changes still use secure persistence when selected.
3. Select **Engine only**, **Execution only**, or **Both logs**. In Paths, choose each folder and filename independently, or use a direct file picker. Check the complete resolved path before starting. The initial engine suggestion is `C:\ProgramData\FIBIC\Atlasengine\atlasengine.log`; its spelling is unverified. The samples also refer to `C:\ProgramData\Fibics\AtlasEngine`. The app will not choose a different folder for you.
4. Use **Validate/Test Read**. Missing/unreadable sources remain visibly waiting and retry on schedule; this does not prevent the other source from working. No administrator elevation or source-directory write permission is needed.
5. Review Rules separately for ENGINE and EXECUTION. Structured Error/Fatal/Critical rules start enabled. Execution fault phrases start enabled. EHT variants, standby, warning levels, and engine candidates are visible optional presets. `WMAcqError` has no validated vendor interpretation here. Use the rule tester before relying on custom phrases.
6. Choose polling seconds (default 10, range 1–3600). Select **New entries only** for routine monitoring. It establishes an end-of-file baseline and avoids alerts for old errors. **Review existing contents** is a historical review with external alerts suppressed. **Resume** uses a saved valid cursor: its initial backlog is also historical and externally suppressed until catch-up ends, unless you explicitly allow historical alerts. It does not replay a previous notification queue automatically.
7. Click **Start monitoring**. Confirm each enabled source card shows its actual access state. Incoming matches appear with their source, logged level, assigned severity, rules and channel status. Acknowledge a fault after reading it; acknowledgment preserves history and does not claim recovery.
8. If activity should continue, deliberately arm **Expect activity** for that source. Execution's starting silence policy is 30 empty successful reads, nominally 300 seconds at a 10-second interval; its heartbeat threshold is also sample-derived. Engine activity checks start unarmed because engine messages can be roughly an hour apart. Configure generous thresholds for autofocus/milling and pauses. Heartbeat alone does not prove imaging progress.
9. Configure and explicitly test [Gmail](gmail.md) and/or [Telegram](telegram.md). Verify the actual received TEST and phone notification behavior. Then check **Enable this external notification channel** for each intended channel and click **Apply settings and rules**. The test buttons do not arm automatic sending.
10. Click **Start alerts** when the paths, active rules, timing policies and enabled channels are correct. The control affects external sending; detection and local history continue with alerts off. Start alerts defaults to future eligible events only. If no channel has been enabled and saved, the app explains what to do instead of arming alerts.

Stopping monitoring also prevents new automatic sends for that monitoring session. Stopping alerts suppresses unsent work from that alert session. Requests already in flight may still be accepted; the eventual outcome is retained. Restarting either control does not quietly send a stale queue. Use explicit resend/discard actions for persisted undelivered events.

Events & history defaults to **Current session only**. Leave it checked to see only this monitoring session; uncheck it to browse stored past events. With New entries only, an editor rewrite no longer triggers a scan from the beginning. If its old cursor cannot be located unambiguously, a coverage warning explains that the new baseline is at the current end and some records added during that rewrite may be missed.

Close-to-tray can leave monitoring running: read the close dialog and tray status. Use **Quit** to terminate. Locking Windows usually leaves the process running; logging out, shutdown, power loss, process termination and sleep interrupt coverage. The same PC cannot report its own complete power or OS failure immediately.

Complete [acceptance.md](acceptance.md) on the microscope workstation using an expendable acquisition before unattended use. Keep a separate laboratory response procedure; a watchdog alert is an observation, not a vendor diagnosis.
